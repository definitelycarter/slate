# Cosmos parity harness

Differential test: run the same queries against **slate** and the **Azure Cosmos
DB Linux emulator**, over the *same* fixture documents, and report divergences.
The cross-engine counterpart to the in-repo v1↔v2 differential tests — here the
oracle is real Cosmos.

Three replays — two hermetic (no Docker), one live:
- **`cargo test -p slate-db --test cosmos_golden`** — our own curated matrices
  (`queries/*.sql`) vs **committed goldens** captured from the emulator (no Docker
  at replay; see "Slate-matrix golden suite" below). **214 / 216 match**; the 2
  remaining are the divide/modulo-by-zero gap, reported as known gaps.
- **`run_samples.py`** — the **Azure-Samples corpus** vs its authoritative
  `result.json` (no emulator needed). Currently **111 / 117 match**; the 6
  remaining are all spatial functions (`ST_*`), not yet implemented in slate.
- **`run.py`** — our own matrices (positive + negative + edge + generated) vs the
  **live emulator**. ~456/507 of these match; nearly all the rest are the emulator
  being wrong (see "Remaining divergences" below), plus divide/modulo-by-zero. This
  is the broad net for what the goldens don't cover (generated subqueries, the full
  scalar-function FROM-less matrix run live).

## Layout

```
datasets/          one JSON file per dataset (single source of truth)
  products.json    from the emulator's bundled SampleDB (floats, bools, tags)
  orders.json      from SampleDB (arrays of line-item objects, nested address)
  families.json    deeply nested arrays/objects, mixed schema, empty arrays
queries/           hand-written matrices + GENERATED matrices (gen_*.sql)
  functions.sql    a FROM-less test for every scalar function we support
  products/orders/families.sql   projection/WHERE/ORDER BY/aggregate/subquery
  negative.sql     queries that should error (parity = both error)
  edge.sql         undefined / JOIN corner cases (parity = same result)
  subquery_perms.sql   the (SELECT … FROM t) … JOIN family
  gen_*.sql        GENERATED by gen.py — subqueries in every position, nesting
gen.py             composes the generated matrices (tune for 1000+)
run.py             emulator harness: recreate, seed per dataset, diff, report
capture_goldens.py capture committed goldens for the curated matrices from the emulator
goldens/           COMMITTED goldens: <label>/<NNN>.json = {query, dataset, result|error}
  _excluded.json   emulator-bug queries we refuse to golden (auditable; currently empty)
  _known_gaps.json real slate gaps: correct Cosmos golden kept, replay reports not asserts
samples_fetch.sh   fetch the Azure-Samples corpus (pinned commit, no history) into .samples/ (gitignored)
run_samples.py     diff slate against the corpus's result.json; categorize gaps
```

Unlike the gitignored `.samples/` corpus, `goldens/` **is committed** — these are
our own fixtures, captured once from the emulator and replayed hermetically in Rust.

The slate side runs in-process three ways, each loading data into an in-memory
slate DB (`pk_path: "id"` to match Cosmos's system key): the `parity_dump.rs`
(live matrices) and `parity_samples.rs` (corpus) `slate-cli` examples, and the
`crates/slate-db/tests/cosmos_golden.rs` test (committed goldens).

## Slate-matrix golden suite

Slate's own curated matrices (`queries/*.sql`) now have a **committed hermetic
golden suite** — the successor to the removed v1↔v2 differential, folded into
`cargo test`. The goldens were captured once from the emulator; replay needs no
Docker and no network:

```bash
cargo test -p slate-db --test cosmos_golden          # hermetic replay (214/216)
python3 tools/cosmos-parity/capture_goldens.py        # re-capture from the emulator (Docker)
python3 tools/cosmos-parity/capture_goldens.py --triage   # report only, write nothing
```

Each `goldens/<label>/<NNN>.json` is `{query, dataset, result | error}` holding
Cosmos's **raw** output (system fields and all). Normalization happens exactly
once, in Rust, at replay time — `cosmos_golden.rs` strips `_`-system fields, sorts
unless the query has `ORDER BY`, and treats whole-valued floats as ints — so the
[Normalization](#normalization) rules live in a single implementation, not
duplicated across Python and Rust.

The capture is self-auditing: it runs slate alongside the emulator and won't
silently pin a divergence. Two committed sidecars govern it:
- `goldens/_excluded.json` — emulator-bug families we refuse to golden (pinning a
  known-wrong oracle is forbidden). **Currently empty**: none of those families
  (subquery as JOIN/aggregate source, COUNT-subquery-in-WHERE, etc.) appear in the
  curated matrices — they live only in the generated `gen_*.sql`, which aren't
  goldened. The live `run.py` still exercises them.
- `goldens/_known_gaps.json` — real slate gaps (the emulator is right, slate
  diverges). The correct Cosmos golden *is* committed, but the replay reports these
  instead of asserting, so the suite stays green while the gap stays pinned. Today:
  `SELECT VALUE 1 / 0` and `SELECT VALUE 5 % 0` (Cosmos errors 400; slate drops the
  row → `[]`).

Generated matrices (`gen_*.sql`) are deliberately **not** goldened — a randomly
generated query has no fixed oracle, so they keep diffing live via `run.py`.

## Azure-Samples corpus

[`Azure-Samples/cosmos-db-nosql-query-samples`](https://github.com/Azure-Samples/cosmos-db-nosql-query-samples)
ships ~140 folders, each with `query.sql`, an authoritative `result.json`, and
optional `seed.json` — so it's an oracle without the emulator. Fetch and run:

```bash
tools/cosmos-parity/samples_fetch.sh      # fetch pinned corpus into .samples/ (gitignored, no history)
python3 tools/cosmos-parity/run_samples.py
```

`samples_fetch.sh` pins a specific upstream commit and drops git history (a single
shallow snapshot), so the 111/117 baseline is reproducible — upstream can't drift
it. Bump the `COMMIT` in that script to update the corpus.

What the 6 non-matches map to (a concrete to-do list):
- **Spatial functions** — `ST_AREA`, `ST_DISTANCE`, `ST_INTERSECTS`, `ST_ISVALID`,
  `ST_ISVALIDDETAILED`, `ST_WITHIN` (not yet implemented in slate).

The earlier backlog — missing scalar functions (trig / integer / string
conversion), the `FROM <container> [AS] <alias>` grammar gap, the arity gaps,
oversized integer literals, and the `IS_NULL` null-vs-undefined bug — has since
closed; see the "Fixed" trail at the end of this README.

## Running

`run.py` manages the emulator itself — it `docker rm -f`s and recreates the
`slate-cosmos` container each run for a clean slate (the emulator persists data
to its container layer, so a restart would keep stale docs). Just run:

```bash
python3 tools/cosmos-parity/run.py
```

Requires Docker and `cargo`. The emulator image is the ARM64-friendly
`mcr.microsoft.com/cosmosdb/linux/azure-cosmos-emulator:vnext-latest`, driven
over HTTP via `docker exec … cosmoshell.sh` (no host ports needed).

## Normalization

Before comparing, results are normalized: Cosmos `_`-prefixed system fields
(`_rid`, `_etag`, `_ts`, …) are stripped, item lists are sorted unless the query
has `ORDER BY`, and **whole-valued floats are compared equal to ints**. That last
point matters: slate is BSON-typed, so its math functions return `Double`
(`SQRT(16)` → `4.0`), whereas Cosmos has a single JSON number type and serializes
whole numbers as `4`. Same value, different representation — 16 queries differ
only this way and are treated as matching.

## Coverage

The matrix includes positive queries (every scalar function, projections,
WHERE, ORDER BY, paging, JOIN, subqueries, aggregates, GROUP BY, nested access),
**negative** tests (`negative.sql` — malformed syntax, unknown functions, wrong
arity, unqualified identifiers — where parity means *both* engines error), and
**edge** behavior (`edge.sql` — undefined/omission and JOIN corner cases, where
parity means the same result, not an error).

Strong agreement on the error surface: every malformed-syntax query, unknown
function, arity error, and `SELECT *`-without-`FROM` is rejected by both engines;
every undefined/omission and JOIN edge case (join on non-array/missing → no rows,
field access on a scalar element → undefined, double join → cross product)
produces identical results.

## Remaining divergences

Real slate gaps:
- **Divide / modulo by zero** (`SELECT VALUE 1 / 0`, `5 % 0`) — the emulator
  raises `400 BadRequest`; slate returns undefined (drops the row). (Confirm
  against hosted Cosmos — but a clear behavioral divergence to track.)
- **Not-yet-implemented functions** — spatial (`ST_*`) and `VECTORDISTANCE`
  (the corpus's remaining slate-errors).

Emulator limitations (oracle is wrong, slate is correct — confirm on hosted Cosmos):
- **Multi-value subquery as a JOIN source** (`JOIN j IN (SELECT …)`) returns `[]`
  in the emulator even when rows should match; slate returns the correct rows
  (the Cosmos docs show this form working).
- **`COUNT` scalar-subquery in `WHERE`** raises an internal `localCount must be a
  number` error in the emulator; slate evaluates it.
- **Aggregate inside a `SELECT VALUE` subquery hoists to the outer query.**
  `SELECT VALUE (SELECT VALUE COUNT(t) FROM t) FROM c JOIN t IN c.tags` returns
  `[5]` (one aggregated row), but the *same* subquery as `SELECT (…) AS n` returns
  five `{n:1}` rows — the projection shape shouldn't change whether the outer
  query aggregates, and the `COUNT` lives inside an independent subquery. slate is
  self-consistent: per-row `1` in both forms. (Use `COUNT(1) FROM c JOIN t IN
  c.tags` for a real total.)
- **Aggregate over a subquery-as-source returns `0`** — `COUNT(1) FROM y IN
  (SELECT VALUE … FROM …)` counts `0` in the emulator (it treats the inner
  subquery's rows as empty); slate counts the real rows. Same root cause as the
  JOIN-source `[]` bug above.
- **`SUM`/aggregate over an empty filtered subquery returns `0`** — e.g.
  `(SELECT VALUE SUM(1) FROM t IN c.tags WHERE STARTSWITH(t, 'a'))` for a row whose
  filter matches nothing: the emulator emits `0`; slate returns undefined and omits
  the field. The largest such family — ~14 queries in the live matrix.

Benign (both arguably valid — neither engine is wrong):
- **`ORDER BY` on a tied key with `OFFSET`/`LIMIT`** returns the page in a different
  order across engines; the sort is only defined up to ties.
- **Large-integer float precision** — `SQUARE(creationDate)` past 2⁵³ diverges in
  the low digits (both f64, rounding differently). Tracked under the number-model
  backlog.

Fixed (kept here as the trail): unqualified identifiers now rejected; FROM
`<container> [AS] alias`; item-scoped `FROM <outer-alias>` subqueries; subqueries
in JOIN/nested-FROM sources; `IS_NULL` of a computed null; oversized integer
literals; trig / integer / bitwise / string-conversion functions; the
3-arg `ARRAY_CONTAINS`/`REGEXMATCH` and 2-arg `ObjectToArray` forms.
