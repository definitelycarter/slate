## 1. What vector search actually is

### 1.1 What an embedding vector is

An **embedding** is a learned, dense list of floating-point numbers that
represents a piece of content (text, image, audio) as a point in a
high-dimensional space. OpenAI's docs define it plainly: an embedding is "a
vector (list) of floating point numbers. The distance between two vectors
measures their relatedness. Small distances suggest high relatedness and large
distances suggest low relatedness."
(<https://developers.openai.com/api/docs/guides/embeddings>)

The defining property is **semantic similarity ≈ geometric proximity**: content
with similar *meaning* lands at nearby points, so "how alike are these two
things?" becomes "how close are their vectors?"
(<https://developers.google.com/machine-learning/clustering/dnn-clustering/supervised-similarity>)

These vectors are **learned** by a neural network (typically a transformer
encoder), often via contrastive training on hundreds of millions of example
pairs. The `all-MiniLM-L6-v2` model card says it "maps sentences & paragraphs to
a 384 dimensional dense vector space" and was fine-tuned on over 1 billion
sentence pairs. (<https://huggingface.co/sentence-transformers/all-MiniLM-L6-v2>)

### 1.2 WHO computes embeddings — the app/model, NOT the database

This is the single most important point for a newcomer:

- **An ML embedding model computes the vectors.** IBM and Databricks both state
  embeddings "are generated by AI models," and the *application* generates them
  before storage.
  (<https://www.ibm.com/think/topics/vector-database>,
  <https://www.databricks.com/blog/what-is-vector-database>)
- **The database stores, indexes, and searches the vectors — it does not generate
  them.** Pinecone: "A vector database indexes and stores vector embeddings for
  fast retrieval and similarity search." At query time you "use the same embedding
  model to create embeddings for the query and use those embeddings to query the
  database for similar vector embeddings."
  (<https://www.pinecone.io/learn/vector-database/>)

So the division of labor is: **application (running an embedding model) →
generates vectors; database → stores + indexes + nearest-neighbor searches them.**
The query vector must come from the *same* model as the stored vectors, or the
geometry isn't comparable. **For Slate this means: Slate stores a `[f32]` field,
builds an index over it, and answers nearest-neighbor queries. Slate does not run
an embedding model.** (The iOS app would use Apple's NaturalLanguage / CoreML
embeddings or call a model; the wasm/JS app would call an API or run a small local
model.)

### 1.3 Typical dimensionality (concrete model → dim numbers)

| Model | Dimensions | Source |
|---|---|---|
| sentence-transformers **all-MiniLM-L6-v2** | **384** | [HF card](https://huggingface.co/sentence-transformers/all-MiniLM-L6-v2) |
| **BERT-base** (and derivatives) | **768** | [Wikipedia](https://en.wikipedia.org/wiki/BERT_(language_model)) |
| **Cohere embed v3** | **1024** (default; configurable 384/768) | [Cohere docs](https://docs.cohere.com/docs/cohere-embed) |
| OpenAI **text-embedding-ada-002** (older) | **1536** | [OpenAI](https://developers.openai.com/api/docs/guides/embeddings) |
| OpenAI **text-embedding-3-small** | **1536** | [OpenAI](https://developers.openai.com/api/docs/guides/embeddings) |
| OpenAI **text-embedding-3-large** | **3072** | [OpenAI](https://developers.openai.com/api/docs/guides/embeddings) |

**Matryoshka / shortening:** the OpenAI v3 models support a `dimensions`
parameter that truncates the vector "without it losing its concept-representing
properties" — a `text-embedding-3-large` vector shortened to **256** dims "still
outperform[s] an unshortened `text-embedding-ada-002` embedding with a size of
1536." This works because the models are trained with Matryoshka Representation
Learning (most important info packed into the earliest dimensions).
(<https://openai.com/index/new-embedding-models-and-api-updates/>,
<https://www.pinecone.io/learn/openai-embeddings-v3/>)

### 1.4 Distance / similarity metrics (with the math)

- **Cosine similarity** — the *angle* between vectors, ignoring magnitude:
  `cos(θ) = (A·B) / (||A|| ||B||)`, range **−1 to +1** (+1 same direction, 0
  orthogonal, −1 opposite). Good for texts of different lengths.
  (<https://en.wikipedia.org/wiki/Cosine_similarity>)
- **Dot product / inner product** — `A·B = Σ Aᵢ Bᵢ`. The un-normalized numerator
  of cosine; **magnitude-sensitive** (a longer vector can score higher just for
  being longer).
  (<https://www.dataquest.io/blog/measuring-similarity-and-distance-between-embeddings/>)
- **Euclidean (L2) distance** — `d(A,B) = sqrt(Σ (Aᵢ − Bᵢ)²)`; smaller = closer;
  also magnitude-sensitive.

**The key relationship — normalization makes them equivalent for ranking.**
L2-normalizing scales every vector to unit length (`||A|| = 1`). Once that's done,
cosine collapses to a plain dot product, and Euclidean distance becomes a
monotonic function of cosine, so **cosine, dot product, and Euclidean all produce
the identical nearest-neighbor ranking.** OpenAI states this verbatim: "Cosine
similarity and Euclidean distance will result in the identical rankings" for their
normalized embeddings. Many models (all-MiniLM, BGE, Cohere v3, OpenAI) emit
normalized vectors, so cosine — equivalently the cheaper dot product — is the
default. OpenAI explicitly "recommend[s] cosine similarity."
(<https://developers.openai.com/api/docs/guides/embeddings>,
<https://en.wikipedia.org/wiki/Cosine_similarity>)

> **Slate implication:** if Slate normalizes vectors at insert time (or documents
> that callers should), it can implement *one* distance kernel (dot product) and
> get cosine ranking for free. This matters because Cosmos parity requires
> `cosine`, `dotproduct`, and `euclidean` (see §2.1).

### 1.5 Exact kNN (brute force) vs Approximate NN (ANN)

- **Exact kNN (brute force):** compare the query to *every* stored vector, keep
  the closest k. **O(N·d)**, guaranteed-correct top-k, but slow at scale —
  brute-forcing 1M × 1536-dim vectors is ~**750 ms/query** on a modern CPU.
  (<https://opensourceconnections.com/blog/2025/02/27/vector-search-navigating-recall-and-performance/>)
- **Approximate NN (ANN):** index structures (HNSW, IVF, PQ, etc.) trade a little
  accuracy for big speedups — the same 1M × 1536 workload drops to **~5–20 ms at
  95–99% recall**, ~100× faster.
  (<https://opensourceconnections.com/blog/2025/02/27/vector-search-navigating-recall-and-performance/>)
- **Recall@k** is the standard quality metric: `|approx top-k ∩ true top-k| / k`,
  ranging 0–1. (<https://arxiv.org/pdf/1807.05614>)
- **The tradeoff triangle:** accuracy (recall) ↔ latency/throughput ↔
  memory/storage. You cannot maximize all three; you tune via knobs like HNSW's
  `ef_search` or IVF's `nprobe`.
  (<https://www.pinecone.io/learn/vector-database/>)

> **Slate implication:** for an *embedded, on-device* DB, the corpora are often
> small (thousands to low-hundreds-of-thousands of vectors). Brute force is
> frequently the *right* answer there, and it maps perfectly onto an ordered-KV
> store (a range scan). This argues for shipping **flat/brute-force first** and
> treating ANN as a later phase — exactly what Cosmos (`flat`) and sqlite-vec do.

## 2. How systems store the vector index on disk

This is the core question. For each system: index structure, on-disk layout,
parameters, tradeoffs.

### 2.1 Azure Cosmos DB for NoSQL (the parity target)

**Container "vector embedding policy"** (`vectorEmbeddings`) declares each vector
property. Fields
(<https://learn.microsoft.com/en-us/azure/cosmos-db/nosql/vector-search>):

- `path` — the document property holding the vectors.
- `dataType` — `float32` (default), `float16`, `int8`, `uint8`.
- `dimensions` — vector length; **default 1536**; all vectors at a path share it.
- `distanceFunction` — `cosine` (default), `dotproduct`, `euclidean`.

```json
{ "vectorEmbeddings": [
  { "path":"/vector1", "dataType":"float32", "distanceFunction":"cosine", "dimensions":1536 }
]}
```

Wildcards and vectors nested inside arrays are **not** supported. The feature must
be enabled per account (`EnableNoSQLVectorSearch`). Policies and indexes are
**immutable** after creation (drop + recreate to change).

**Vector index TYPES** (the heart of it)
(<https://learn.microsoft.com/en-us/azure/cosmos-db/nosql/vector-search>,
<https://learn.microsoft.com/en-us/azure/cosmos-db/index-policy>):

| Type | What it is | Search | Max dims |
|---|---|---|---|
| **`flat`** | Full vectors stored on the standard index | Brute-force, **100% recall** | **505** |
| **`quantizedFlat`** | Quantized (compressed) vectors on the index | Brute-force, slightly <100% | **4096** |
| **`diskANN`** | DiskANN/Vamana graph | Approximate (ANN) | **4096** |

- **`flat`** — stores each full vector and reads them all during search; exact,
  "guaranteed to find the most similar vectors." Hard 505-dim limit.
- **`quantizedFlat`** — stores product-quantized vectors; still brute-force but
  cheaper (lower latency/RU). Recommended "when the number of vectors scoped to
  your search is **50,000 or fewer**" (or when WHERE filters narrow candidates).
- **`diskANN`** — separate DiskANN graph index; ANN, "the most performant of all
  index types if your search query is scoped to **more than 50,000 vectors**."

**Build parameters** (<https://learn.microsoft.com/en-us/azure/cosmos-db/index-policy>):

- `quantizationByteSize` — product-quantization size in bytes. **Min 1, default
  dynamic, max 512.** Applies to `quantizedFlat` and `diskANN`.
- `indexingSearchListSize` — vectors searched during graph build. **Min 10,
  default 100, max 500.** `diskANN` only.
- `quantizerType` — `product` (default) or `spherical` (preview).

Both `quantizedFlat` and `diskANN` **require ≥1,000 inserted vectors** for the
quantization to be accurate; below that a full scan runs.

**`VECTORDISTANCE` system function**
(<https://learn.microsoft.com/en-us/azure/cosmos-db/nosql/query/vectordistance>):

```
VECTORDISTANCE(<vector1>, <vector2>, <bruteForce_bool>, <spec_obj>)
```

- Returns a numeric similarity score; vectors are 1-D arrays of
  float32/float16/int8/uint8.
- `bruteForce` (optional): `true` forces a full scan; `false` (default) **uses any
  defined vector index**.
- `spec_obj` (optional): `{ distanceFunction: 'Cosine'|'DotProduct'|'Euclidean',
  dataType: 'Float32'|..., searchListSizeMultiplier, quantizedVectorListMultiplier,
  filterPriority }`. (Note the **capitalized** values in the spec object vs.
  lowercase in the policy.)

Nearest-neighbor usage puts it in `ORDER BY` with a `TOP k`:

```sql
SELECT TOP 10 c.title, VectorDistance(c.contentVector, [1,2,3]) AS score
FROM c
ORDER BY VectorDistance(c.contentVector, [1,2,3])
```

Docs stress: **always use `TOP N`** (otherwise RU/latency blow up).

**Limits:** dims per type 505/4096/4096; ≥1,000 vectors for ANN/quantized;
multiple vector properties allowed if each targets a distinct path; not supported
on shared-throughput accounts; can't be disabled once enabled.

**DiskANN/Vamana** — a Microsoft Research ANN suite; its core graph **Vamana**
"maintain[s] accuracy despite many insertions, modifications, and deletions,
without the need for expensive index rebuilds" — which is why Cosmos chose it over
HNSW (whose merges/rebuilds are costly). "DiskANN vector indexes are stored on
high-speed SSDs, while compressed vectors are stored in memory."
(<https://devblogs.microsoft.com/cosmosdb/introducing-vector-database-capabilities-in-azure-cosmos-db-for-nosql/>,
<https://devblogs.microsoft.com/cosmosdb/diskann-for-azure-cosmos-db-now-in-open-public-preview/>,
<https://www.microsoft.com/research/publication/diskann-fast-accurate-billion-point-nearest-neighbor-search-on-a-single-node/>)

> **Parity takeaway:** to match Cosmos, Slate needs `VECTORDISTANCE` with the same
> signature/semantics and a `cosine`/`dotproduct`/`euclidean` choice. Slate's
> `flat` ≈ Cosmos `flat` (exact, low dims). Slate's later ANN can borrow the
> *DiskANN layout* (graph + full vectors on disk, PQ codes in RAM) precisely
> because that layout is disk-resident — a natural fit for a KV store (§3.6).

### 2.2 MongoDB Atlas Vector Search (Lucene HNSW, segment storage)

- **Engine:** runs in a separate process `mongot`, "built on Apache Lucene,
  leveraging its native KNNVectorField support and the Hierarchical Navigable
  Small World (HNSW) algorithm."
  (<https://foojay.io/today/power-your-ai-application-with-vector-search/>,
  <https://www.mongodb.com/company/blog/product-release-announcements/now-source-available-the-engine-powering-mongodb-search>)
- **On-disk layout — Lucene immutable segments.** Data streams from `mongod` via
  Change Streams and is "written to **Lucene segment files**." Each immutable
  segment stores **its own HNSW graph**; new writes create new segments;
  background **merges** consolidate small segments (rebuilding/merging their HNSW
  graphs) — an LSM-like compaction model. Deletes are tombstoned.
  (<https://foojay.io/today/power-your-ai-application-with-vector-search/>)
- **`$vectorSearch` stage** (must be first):
  `index`, `path`, `queryVector`, `numCandidates`, `limit`, `filter`, `exact`.
  (<https://www.mongodb.com/docs/atlas/atlas-vector-search/vector-search-stage/>)
  - **`numCandidates` vs `limit`:** `numCandidates` is the **ANN search width** —
    how many candidates the HNSW traversal considers before returning the top
    `limit`. Must be `≥ limit` and `≤ 10,000`. Docs recommend **10–20× `limit`**.
    Only used for ANN; **omit it for `exact: true`** (ENN exhaustive search).
- **Index definition:** `fields` with `type: "vector"` (`path`, `numDimensions`
  1–4096, `similarity` ∈ {euclidean, cosine, dotProduct}, `quantization`) plus
  `type: "filter"` fields you must declare to pre-filter on.
  (<https://www.mongodb.com/docs/atlas/atlas-vector-search/vector-search-type/>)
- **Quantization** (<https://www.mongodb.com/docs/vector-search/about/vector-quantization/>):
  `scalar` (float32→int8) and `binary` (float32→1 bit) with rescoring.
  **Automatic quantization reduces mongot RAM by 3.75× (scalar) / 24× (binary);
  the raw values shrink 4× / 32×.** Binary "retain[s] up to 95% search accuracy."
  **Critically for storage: full-fidelity vectors are still kept on disk** in a
  separate structure for rescoring/exact search — quantization saves **RAM, not
  total disk footprint**. Recommended for >100K (and especially >1M) vectors.
  (<https://www.mongodb.com/company/blog/product-release-announcements/binary-quantization-rescoring-96-less-memory-faster-search>)
- **Dims ≤ 4096.** Filtering is pre-filter (before ANN); filtered queries are
  "typically slower than an otherwise equivalent unfiltered query."

### 2.3 pgvector (Postgres extension)

Primary source: <https://github.com/pgvector/pgvector>. Both index types are real
Postgres **index access methods** (`USING hnsw` / `USING ivfflat`), so the graph /
lists live **in Postgres index pages** and participate in WAL, buffer cache, and
`VACUUM` — in-process, unlike MongoDB's out-of-process `mongot`.

- **IVFFlat:** k-means produces `lists` centroids; each vector goes in its nearest
  centroid's posting list; query probes `ivfflat.probes` (default 1) nearest
  lists. **Must be built AFTER data is loaded** (needs data to train centroids).
  Recommended `lists` = `rows/1000` (≤1M rows) or `sqrt(rows)` (>1M). On disk:
  centroids + flat (unquantized) posting lists. Generally **smaller on disk than
  HNSW** but worse speed/recall.
- **HNSW:** multilayer graph in index pages. Build params `m` (default 16),
  `ef_construction` (default 64); query param `hnsw.ef_search` (default 40).
  **No training step — can be built incrementally on an empty table.** Better
  speed/recall than IVFFlat but slower builds, more memory, larger index.
- **Distance operators:** `<->` L2, `<#>` negative inner product, `<=>` cosine,
  `<+>` L1; (`<~>` Hamming, `<%>` Jaccard for `bit`).
- **Vector types & quantization (via type choice, not an index flag):**
  - `vector` (float32): **`4*dims + 8` bytes**; indexable up to **2,000** dims.
  - `halfvec` (float16): `2*dims + 8` bytes; halves storage; indexable up to
    **4,000** dims.
  - `bit` (binary): `dims/8 + 8` bytes; indexable up to **64,000** dims (Hamming).
  - `sparsevec`: `8*nnz + 16` bytes.
  - Quantization = choose `halfvec` or `bit`; pgvector recommends "half-precision
    indexing or binary quantization for smaller indexes." (No automatic rescoring,
    unlike MongoDB.)

> **Storage note for Slate:** a 1536-dim float32 `vector` = **6,152 bytes** — this
> is the per-vector cost that dominates on-device footprint (§6.5).

### 2.4 Embedded / on-device comparables (MOST relevant to Slate)

At-a-glance:

|---|---|---|---|---|---|---|---|

**LanceDB / Lance** — index = `{clustering}_{sub_index}_{quantization}` where
clustering is always IVF, sub-index FLAT/HNSW, quantization PQ/SQ/RQ/FLAT;
**IVF_PQ is the default**. Vectors and index persist as regular **Lance columnar
files** (page-based, ~8MB pages, no row groups, footer + "LANC" signature),
designed for out-of-core random access (read tail → footer → fetch only needed
page byte-ranges). Indexes live under `_indices/{UUID}/`. Rust core, Apache-2.0 —
**but wasm is explicitly shelved** ("tokio does not run on wasm... lance relies a
lot on tokio"), and the arrow/datafusion/object_store stack is heavy for iOS.
*Excellent design reference, not a drop-in dependency.*
(<https://github.com/lancedb/lance/blob/main/docs/src/format/index/vector/index.md>,
<https://github.com/lancedb/lance/blob/main/docs/src/format/file/index.md>,
<https://github.com/lancedb/lance/issues/680>)

**sqlite-vec** (successor to the deprecated, Faiss-backed **sqlite-vss**) — the
closest *storage* analog to "vectors-in-the-DB." It's **brute-force only today**
("There will be no 'approximate nearest neighbors' (ANN) options" yet; IVF+HNSW on
the [roadmap](https://github.com/asg017/sqlite-vec/issues/25)) and stores vectors
**inside SQLite via chunked shadow tables**, "just like fts5," read chunk-by-chunk.
Single C file, no deps, "runs anywhere SQLite runs... in the browser with WASM";
iOS "theoretical" (compile the C yourself). Element types float32/int8/binary;
`vec_quantize_binary()` for 32×. Apache-2.0/MIT.
(<https://alexgarcia.xyz/blog/2024/sqlite-vec-stable-release/index.html>,
<https://github.com/asg017/sqlite-vec/blob/main/README.md>)

**Faiss** — the *vocabulary* (Flat/IVFFlat/IVFPQ/PQ/HNSW) everyone borrows.
Persists via **monolithic `write_index`/`read_index`** to one file (or
`OnDiskInvertedLists` `.ivfdata` for huge IVF) — **not a KV store, no incremental
on-disk mutation.** C++ with BLAS/OpenMP deps; no official wasm/iOS; from Rust via
the community `faiss` crate over a C API. MIT.
(<https://github.com/facebookresearch/faiss/wiki/Faiss-indexes>,
<https://github.com/facebookresearch/faiss/wiki/Index-IO,-cloning-and-hyper-parameter-tuning>)

**USearch** — **strongest off-the-shelf on-device fit.** Single-header C++11 HNSW,
**no obligatory dependencies**, explicit platforms "Linux • macOS • Windows • iOS
• Android • WebAssembly," official **Swift** (real on-device
[SwiftSemanticSearch](https://github.com/ashvardanian/SwiftSemanticSearch) app) and
**Rust** bindings, i8/binary down/up-casting. Key property: **single mmap-able
index file with view-from-disk** — "Viewing the index does not load the data into
memory... traverse the index structure from external memory using memory-mapping,"
and you can `view_from_buffer` an mmap you manage, i.e. **store the serialized
index as a KV blob and hand USearch a view.** Apache-2.0. *Friction:* the Rust path
is `cxx` C++ FFI (needs a C++ toolchain), and the wasm route is the JS binding, not
the Rust crate.
(<https://github.com/unum-cloud/usearch>,
<https://unum-cloud.github.io/usearch/>,
<https://unum-cloud.github.io/usearch/swift/>)

**Qdrant** — Rust vector DB, **server-oriented** (the embeddable "Qdrant Edge —
think SQLite but for vector search" is **private beta**). Modified "filterable
HNSW" (extra edges so filtered subgraphs stay connected). **The most strategically
relevant data point in this whole survey:** Qdrant started on **RocksDB** (Slate's
stack) for payload/sparse-vector storage and is **replacing it with a custom KV
engine, "Gridstore,"** to escape LSM-compaction "random latency spikes" — "In
Qdrant v1.17.x we will completely remove RocksDB support in favor of gridstore."
Quantization: scalar (4×), product (up to 64×), binary (up to 32×). Apache-2.0.
(<https://qdrant.tech/articles/gridstore-key-value-storage/>,
<https://qdrant.tech/articles/filtrable-hnsw/>,
<https://qdrant.tech/blog/qdrant-edge/>)

**Weaviate** — Go, HNSW + flat, server-only (embedded mode is dev/test only).
LSM-tree KV per shard + mmap + HNSW snapshots. BSD-3. Not an on-device option and
Go doesn't fit a Rust/wasm/iOS story.
(<https://docs.weaviate.io/weaviate/concepts/storage>)

**arroy** (Meilisearch) — **the direct KV-store architectural template.** A Rust
reimplementation of Spotify's **Annoy** (forest of random-projection trees), with
filtered querying, **incremental indexing**, and atomic multi-index storage — all
persisted as **LMDB key-value entries**. The concrete scheme is worth copying:
**value** = a `Node` enum with a leading tag byte (`Leaf` tag 0 = header +
vector; `Descendants` tag 1 = a RoaringBitmap; `SplitPlaneNormal` tag 2 =
left/right NodeId + hyperplane); **key** = 5 bytes (`NodeMode` byte +
big-endian u32 `ItemId`), giving ordered range scans within a mode. Reads are
mmap (LMDB gives a pointer into the mapped file). **Catch:** persistence depends on
LMDB (C) via `heed`, which **does not compile to wasm32/WASI** — so for Slate you'd
*reimplement the scheme over your own store*, not depend on arroy. MIT.
(<https://github.com/meilisearch/arroy/blob/main/README.md>,
<https://docs.rs/arroy/latest/src/arroy/node.rs.html>,
<https://docs.rs/arroy/latest/src/arroy/node_id.rs.html>,
<https://github.com/meilisearch/heed/issues/162>)

**Pure-Rust ANN crates (the wasm/iOS-safe building blocks):**

- **hnsw_rs** — pure-Rust HNSW; `hnswio` dump/reload via serde+bincode, plus a
  `datamap` module that mmaps the *data vectors* (not the graph). No C deps.
  MIT/Apache-2.0.
  (<https://github.com/jean-pierreBoth/hnswlib-rs/blob/master/README.md>)
- **instant-distance** — "Fast pure-Rust implementation of the HNSW paper" (powers
  Instant Domain Search). Persistence = optional serde on the `Hnsw`/`HnswMap`
  types; **caller chooses the format and owns I/O** — a clean fit for "serde →
  bytes → write to a KV value." No C deps. MIT/Apache-2.0.
  (<https://github.com/instant-labs/instant-distance/blob/main/README.md>)

Neither README *certifies* wasm/iOS, so a `cargo build --target
wasm32-unknown-unknown` smoke test is the gate before committing.

## 3. The ANN index algorithm families

Throughline: how each lays out on disk and whether it fights an ordered-KV
substrate.

### 3.1 Flat / brute-force (exact)

Store every raw vector contiguously; at query time compute distance to all N and
keep top-k. No structure, no params, no training; **the only index that guarantees
exact results**. Storage = **`4*d` bytes/vector** (float32), total `N*d*4`. Query
O(N·d). Right choice for small N / few queries / on-device — Faiss literally
recommends "brute-force search without an index" for small mobile corpora.
(<https://github.com/facebookresearch/faiss/wiki/Guidelines-to-choose-an-index>,
<https://github.com/facebookresearch/faiss/wiki/Brute-force-search-without-an-index>)

### 3.2 IVF (inverted file index)

k-means trains `nlist` coarse centroids → Voronoi cells; each vector joins its
nearest centroid's posting list; query probes the `nprobe` nearest cells (scans
~`nprobe/nlist` of the DB). Params: `nlist` (Faiss rule `4*sqrt(N)`–`16*sqrt(N)`),
`nprobe` (the recall/speed knob; `nprobe=nlist` ⇒ exact). **Requires a training
step.** On disk: a **centroid table** (`nlist*d*4`) + **posting lists** ("vectors
of each cluster stored contiguously into inverted lists"); `IndexIVFFlat` =
`4*d + 8` bytes/vector. Recall loss at cell boundaries.
(<https://github.com/facebookresearch/faiss/wiki/Faiss-indexes>,
<https://arxiv.org/pdf/1102.3828>)

### 3.3 Quantization (PQ / SQ / BQ)

- **Product Quantization (PQ)** — split a vector into `m` subvectors; k-means
  codebook (`k*=256`) per subspace; store `m` 1-byte codes. Code length
  `m*log2(k*)` bits; e.g. 128-D floats (512 B) → 4 bytes (16×). **ADC** (query
  full-precision, DB codes) builds an `m×256` lookup table and sums `m` lookups
  per vector. Usually combined with IVF (**IVFADC**), the billion-scale recipe.
  Requires training. (<https://arxiv.org/pdf/1102.3828>)
- **Scalar Quantization (SQ)** — float32→int8 per dim, **4×**; ~99% of float32
  recall (~99.3% with rescoring); int8 SIMD ~2–4× faster. The usual default.
  (<https://qdrant.tech/articles/what-is-vector-quantization/>,
  <https://huggingface.co/blog/embedding-quantization>)
- **Binary Quantization (BQ)** — 1 bit/dim, **32×**; distance = Hamming
  (XOR+popcount, ~2 CPU cycles). Big recall loss mitigated by **rescoring**:
  over-fetch with cheap binary distance, re-rank the shortlist with full-precision
  vectors (~92.5% retained alone, ~96% with rescore, ~24.76× speedup).
  (<https://huggingface.co/blog/embedding-quantization>)

**Storage-relevant pattern:** quantized codes are the hot, RAM-resident search
structure; **full-precision vectors only need fetching for the small rerank
shortlist** — a natural "codes in RAM, floats fetched by id from the KV store" fit.

### 3.4 HNSW (graph)

Multi-layer proximity graph; element max-layer drawn from an exponentially
decaying distribution (sparse upper layers = long-range links; layer 0 holds all).
Greedy top-down search → **logarithmic complexity**. Params: `M` (5–48 connections;
`Mmax0=2M`), `efConstruction` (build), `ef`/`ef_search` (the query recall knob); no
training. (<https://arxiv.org/abs/1603.09320>)

**Why it's RAM-hungry:** memory ~ proportional to `M` (Faiss `IndexHNSW` =
`d*4 + M*2*4` bytes/vector — full floats **plus** the graph). Search is
**random-access pointer-chasing**, and hops are **serially dependent** (the next
node depends on the previous hop's result), defeating prefetch — so "the HNSW graph
structure... is kept in RAM even in mmap mode." **Why it's hard to persist
incrementally / merge:** inserts mutate adjacency of arbitrary scattered nodes
(random in-place writes, hostile to append-only/immutable-segment layouts); Faiss
`IndexHNSW` "does not support removing vectors"; merging two HNSW graphs requires
re-linking across both.
(<https://github.com/facebookresearch/faiss/wiki/Guidelines-to-choose-an-index>,
<https://qdrant.tech/articles/memory-consumption/>,
<https://arxiv.org/pdf/2505.17152>)

### 3.5 DiskANN / Vamana (disk-resident graph)

A **single flat graph** (no layer hierarchy). The Vamana build runs greedy-search +
**RobustPrune** twice; **`alpha`** (≈1.2) keeps long-range "shortcut" edges so
fewer hops are needed → "shortest average search path... compared to NSG and HNSW"
→ fewer disk reads. Params: `R` (degree, e.g. 128), `L` (search list), `alpha`.
**On-disk layout — the template for a disk/KV store:**

- **On SSD:** graph adjacency **and** full-precision vectors, **co-located per node
  in sector-aligned (4096 B) blocks** — one read fetches a node's vector + its
  neighbor list.
- **In RAM:** **PQ-compressed vectors** for the whole set, for fast approximate
  distances during traversal.

Random IO is cut by **beam search** (load W non-visited nodes' neighbors per step,
batching SSD latency) and **hot-node caching** (cache the entry region, ~3–4 hops).
Result: SIFT1B (1B points) on **64GB RAM + a commodity SSD** → >5000 QPS, <3ms
mean latency, 95%+ recall, where in-RAM methods plateau ~50%.
(<https://milvus.io/blog/2021-09-24-diskann.md>,
<https://www.microsoft.com/en-us/research/publication/diskann-fast-accurate-billion-point-nearest-neighbor-search-on-a-single-node/>,
<https://cmuparlay.github.io/ParlayANN/algorithms.html>)

### 3.6 KV / LSM substrate mapping (critical for Slate)

An ordered-KV store (RocksDB/redb — sorted byte keys, range scans, point gets) is
**not** an mmap'd contiguous float array, which is what most graph ANN assumes.

- **Flat — maps trivially.** `key = doc_id`, `value = raw vector bytes`; full scan
  = **range scan**, the best access pattern an LSM/B-tree offers (sequential,
  block-cache-friendly, prefetchable). No random gets, no pointer-chasing. For
  small/on-device corpora this is natural and arguably optimal.
- **IVF — maps cleanly.** Centroid table = a few KV entries; posting lists =
  `key = (centroid_id, doc_id)` → all members of a probed cell are a **contiguous
  key prefix** → **one range scan per probed cell**. `nprobe` cells = `nprobe`
  sequential scans. Training is offline.
- **Graph (HNSW/Vamana) — the hard case.** `key = node_id`, `value = neighbor_ids
  [+ vector/PQ code]` is *expressible*, but greedy search = **random KV `get`s**
  that are **serially dependent** (no batch, no prefetch). LSM-VEC formalizes this:
  HNSW "is designed assuming O(1) random access to neighbors," which "breaks down
  in disk-based systems" because "each neighbor lookup requires a separate KV get
  operation." An LSM `get` may touch multiple sorted runs / bloom filters / SST
  blocks; a B-tree `get` is a root-to-leaf descent — both far costlier than a
  pointer deref. (<https://arxiv.org/pdf/2505.17152>)

**The one-sentence tension:** the operation graph search does most often (random
neighbor access) is the operation a KV store does *worst*, whereas flat-scan and
IVF lean on range scans, which a KV store does *best*.

**Proof graph-ANN-on-KV is viable + the mitigation playbook:**

- **arroy/Hannoy (Meilisearch)** persist ANN structures as **LMDB KV entries** in
  production; Hannoy moves the *graph* onto KV.
  (<https://github.com/meilisearch/arroy>,
  <https://blog.kerollmops.com/from-trees-to-graphs-speeding-up-vector-search-10x-with-hannoy>)
- **DiskANN's layout is the KV design template:** co-locate neighbors + vector in
  one value (one `get` returns both), keep PQ codes in RAM (avoid a `get` per
  distance), batch reads (beam search), cache hot entry nodes.
- **LSM-VEC** is the academic point design for graph ANN over an LSM KV store.
  (<https://arxiv.org/pdf/2505.17152>)

> Caveat: the per-vector byte formulas above are Faiss's; a redb/RocksDB-backed
> implementation adds per-key/per-value KV overhead (key bytes, SST/page framing,
> compression) on top — treat them as lower bounds.

## 4. Use cases

### 4.1 RAG (Retrieval-Augmented Generation)

**The full pattern.** *Indexing (offline):* split documents into **chunks** →
embed each chunk → store the vector alongside the chunk text + metadata.
*Retrieval + generation (query time):* embed the user's question with the **same
model** → nearest-neighbor retrieve the **top-k** most similar chunks → stuff them
into the LLM prompt as context → the LLM generates a **grounded** answer. Pinecone
walks exactly this pipeline.
(<https://www.pinecone.io/learn/retrieval-augmented-generation/>)

Origin: **Lewis et al., "Retrieval-Augmented Generation for Knowledge-Intensive NLP
Tasks," arXiv:2005.11401 (NeurIPS 2020)** — combine **parametric memory** (a
seq2seq model) with **non-parametric memory** (a dense vector index accessed by a
neural retriever). (<https://arxiv.org/abs/2005.11401>)

**Why an embedded / on-device vector DB is compelling for RAG:**

- **Privacy** — data never leaves the device; RAG "can be performed directly on
  your mobile device, prioritizing privacy, low latency, and offline
  capabilities."
  (<https://objectbox.io/retrieval-augmented-generation-rag-with-vector-databases-expanding-ai-capabilities/>)
- **Offline** — "eliminates the requirement for internet access."
- **No per-query API cost** — "eliminates the need for cloud inference."
  (<https://deepsense.ai/blog/implementing-small-language-models-slms-with-rag-on-embedded-devices-leading-to-cost-reduction-data-privacy-and-offline-use/>)
- **Low latency** — solid for the *retrieval* step (no network hop). *Caveat:*
  on-device *generation* can still be slow (~5–10 tok/s on phones); scope the
  latency win to retrieval, lead with privacy/offline/cost.

> This is the headline use case for Slate: a private, offline, on-device knowledge
> base where Slate is the retrieval layer (chunks + vectors + metadata in one
> document store) feeding Apple/on-device LLMs.

### 4.2 "Vectorizing documents," hybrid search, metadata filtering

- **The DB stores vectors; the app generates them.** MongoDB: "store vector
  embeddings alongside your other MongoDB data"; you "write a script... [that] uses
  an embedding model" to "Create embeddings from your data and store them," and at
  query time "Create embeddings from your search terms and run a vector search."
  Vectors live as an array field next to operational data.
  (<https://www.mongodb.com/docs/atlas/atlas-vector-search/create-embeddings/>)
- **Hybrid search** — combine lexical (BM25 / full-text) with dense vector
  retrieval, fused via **Reciprocal Rank Fusion (RRF)**. Azure: "Hybrid search
  combines results from both full-text and vector queries, which use different
  ranking functions such as BM25 for text, and HNSW... for vectors. An RRF
  algorithm merges the results."
  (<https://learn.microsoft.com/en-us/azure/search/hybrid-search-overview>)
  - **RRF formula:** `RRF(d) = Σ_r 1/(k + rank_r(d))`, **k typically 60**. Azure:
    "The score is calculated as `1/(rank + k)`... the algorithm performs best when
    you set `k` to a small value, such as 60," summed across systems.
    (<https://learn.microsoft.com/en-us/azure/search/hybrid-search-ranking>) Origin:
    **Cormack, Clarke & Büttcher, SIGIR 2009**
    (<https://cormack.uwaterloo.ca/cormacksigir09-rrf.pdf>).
- **Metadata filtering (very important for a document DB).** Combining a filter
  (`tenant_id`, `date`, `category`, permissions) with vector search:
  - **Pre-filter** (filter candidates BEFORE ANN) — more relevant, but **can break
    ANN graph connectivity**; Pinecone notes pre-filter "disrupts how ANN engines
    work," and Qdrant: low-cardinality filters "disrupt the connections within the
    graph... causing lower accuracy."
  - **Post-filter** (filter AFTER ANN) — simpler/faster, but **may return fewer
    than k** ("very few or even zero results"), and "you're limited to filtering
    only from the initial set of vector search results."
  (<https://www.pinecone.io/learn/vector-search-filtering/>,
  <https://qdrant.tech/articles/vector-search-filtering/>)

> For Slate this is the killer feature: it's *already* a document DB with
> secondary indexes and a query planner. "Filter by collection/owner/date, then
> rank by `VECTORDISTANCE`" is exactly the pre/post-filter problem — and Slate can
> reuse its existing sargability/index machinery for the metadata predicate.

### 4.3 Other use cases (each sourced)

- **Semantic search** — search by meaning; "results ranked by relevance to a query
  string." (<https://developers.openai.com/api/docs/guides/embeddings>)
- **Recommendations / similar-items** — "items with related text strings are
  recommended." (same)
- **Deduplication / near-duplicate detection** — flag pairs whose vectors are very
  close (cosine above a threshold), catching semantic dupes exact hashing misses.
  (<https://zilliz.com/ai-faq/how-do-i-use-embeddings-for-duplicate-detection>)
- **Classification via kNN** — "text strings classified by their most similar
  label" (majority label of the k nearest neighbors).
  (<https://developers.openai.com/api/docs/guides/embeddings>)
- **Anomaly / outlier detection** — "outliers with little relatedness are
  identified" (normal data clusters tightly; anomalies sit in sparse regions).
  (same)
- **Image / multimodal search** — CLIP maps images and text into one shared vector
  space.
  (<https://www.elastic.co/search-labs/blog/multimodal-image-retrieval-with-roboflow>)

## 5. The commissioner's specific questions

### 5.1 "Is vector distance used for map plotting?"

**No — not directly, and the two distances are fundamentally different things.**

- **Geospatial distance** is a **2D distance on Earth's surface** from
  (lat, long) via Haversine / great-circle (or Vincenty on the WGS84 ellipsoid),
  exposed as `ST_DISTANCE`. **Slate already has this** (Vincenty in
  `slate-eval`'s `geo/metric.rs`; see §6). It is 2 dimensions.
  (<https://en.wikipedia.org/wiki/Haversine_formula>,
  <https://postgis.net/docs/ST_Distance.html>)
- **Embedding distance** is computed over **hundreds to thousands of dimensions**
  (e.g. 1536-D) and is what the vector index searches. **These are not
  interchangeable** — geospatial distance is not a special case of embedding
  distance, and `VECTORDISTANCE` is not a geo function.

**BUT** you *can* visualize embeddings on a 2D/3D plot by **reducing
dimensionality first** — a downstream analytics/visualization step, **not what the
index does at query time**:

- **PCA** — linear projection onto top-variance components.
  (<https://scikit-learn.org/stable/modules/generated/sklearn.decomposition.PCA.html>)
- **t-SNE** — van der Maaten & Hinton, JMLR 2008: "visualizes high-dimensional
  data by giving each datapoint a location in a two or three-dimensional map."
  (<https://www.jmlr.org/papers/v9/vandermaaten08a.html>)
- **UMAP** — McInnes, Healy, Melville, arXiv:1802.03426 (2018); preserves more
  global structure than t-SNE. (<https://arxiv.org/abs/1802.03426>)

The OpenAI cookbook demonstrates exactly this: "use t-SNE to reduce the
dimensionality of the embeddings from 1536 to 2" for a scatter plot — *separate
from retrieval*, which still runs on the full 1536-D vectors.
(<https://developers.openai.com/cookbook/examples/visualizing_embeddings_in_2d>)

**Bottom line:** map plotting of *geographic* points uses 2D geospatial distance
(`ST_DISTANCE`, already in Slate); plotting *embeddings* uses dimensionality
reduction for visualization. Neither is the high-D distance the vector index
computes. **Dimensionality reduction is out of scope for the DB** — it's an
app-side analytics task.

### 5.2 "How about clusters?"

You can **cluster embeddings to discover topics / group documents** — a
user-facing analytics task:

- **k-means** — partition into k clusters minimizing within-cluster variance; k
  given up front. (<https://scikit-learn.org/stable/modules/clustering.html#k-means>)
- **HDBSCAN** — density-based, hierarchical; finds variable-density clusters
  *without* presetting k. (<https://scikit-learn.org/stable/modules/clustering.html#hdbscan>)
- Workflow: run k-means/HDBSCAN on stored embeddings to "discover valuable, hidden
  groupings," then label each cluster (often with an LLM).
  (<https://developers.openai.com/cookbook/examples/clustering>)

**The crisp distinction the commissioner needs — "clustering" means two different
things:**

1. **Clustering as an internal index mechanism.** The **IVF** vector index runs
   **k-means at build time** to partition the space into cells (centroids); at
   query it searches only the cells nearest the query (tuned by `nprobe`). Here the
   clusters are **invisible plumbing** — a pure speed optimization, never returned
   to the user. (<https://www.pinecone.io/learn/series/faiss/vector-indexes/>)
2. **Clustering as a user-facing analytics task.** Here k-means/HDBSCAN produces
   the **groupings themselves** as the deliverable (documents grouped by topic).
   The clusters **are** the output. (<https://developers.openai.com/cookbook/examples/clustering>)

Same algorithm, two purposes. An IVF index "clustering" your vectors does **not**
give users a topic-grouped view — that requires running clustering as a *separate
analytics step* on the stored embeddings. (Whether Slate exposes a user-facing
clustering API is a separate product decision from whether it builds an IVF index.)

## 6. Design considerations for Slate

Slate context (verified against the worktree at `.claude/worktrees/vector-index-spike`):

- **Store trait** (`crates/slate-store/src/store.rs`): `get`, `multi_get`,
  `scan_prefix`/`scan_prefix_rev`, **`scan_range(cf, range, reverse)`** (recently
  added), `put`/`put_batch`, `delete`/`delete_batch`, `create_cf`/`drop_cf`. Three
  backends: RocksDB, redb (pure Rust), in-memory.
- **Index encoding** (`crates/slate-engine/src/encoding/`): ordered byte keys
  `i\0{collection}\0{field}\0{value_bytes}{doc_id_lp}`; value-side metadata holds
  per-component type bytes + cumulative end-offsets (u32 LE) + optional TTL, so the
  read path recovers boundaries in O(1). Numeric values are projected onto a
  unified sortable f64 key.
- **Spatial:** `ST_DISTANCE`/`ST_AREA`/`ST_WITHIN`/`ST_INTERSECTS` exist as
  *functions only* (`crates/slate-eval/src/functions/`, geodesy in
  `geo/metric.rs`, pure-Rust/wasm-safe); **there is no spatial index yet** —
  spatial predicates do full scans. (Relevant precedent: function-first, index-later.)
- **Function dispatch:** `crates/slate-eval/src/functions/mod.rs` `call(name, args)`
  uppercases and matches on the name; a `VECTORDISTANCE` would add
  `vectordistance.rs` + one match arm.
- **Index types:** currently just `IndexSpec { path, unique }` /
  `IndexOptions { unique }` (encoded as `[0x01]` for unique); no index-type enum.
  Sargability lives in `crates/slate-planner/src/sargable.rs` (`IndexAccess` enum).
- **Crates:** `slate-store` (KV) · `slate-rawbson` · `slate-engine` (encoding/
  indexes/catalog/txn) · `slate-ast` · `slate-query` (Mongo find) · `slate-sql`
  (Cosmos SQL) · `slate-eval` (functions/eval) · `slate-planner` · `slate-executor`
  · `slate-vm` · `slate-db` (public API) · `slate-uniffi` (Swift/Kotlin) ·
  `slate-wasm` (JS) · `slate-cli`.

### 6.1 Where does the vector live — BSON field, index, or both?

Consensus across systems: **both.** The vector is a normal field in the BSON
document (an array of floats — pgvector, MongoDB, Cosmos all store it as a document
field). The index is a *separate structure* derived from that field. MongoDB and
DiskANN additionally keep **full-precision vectors on disk for rescoring even when
the index stores quantized copies** (§2.2, §3.3) — so "both" can mean the float
vector lives in the doc, the index holds quantized codes, and rescoring reads the
doc's floats.

For Slate the cleanest model mirrors existing secondary indexes:
- **Vector field** = a BSON array on the document (source of truth).
- **Vector index** = a dedicated column family / keyspace built from that field.
  For **flat**, the index can even be *thin* (just `doc_id → vector bytes`, or just
  reuse the document) since brute force is a scan.

### 6.2 Pure-Rust ANN crate options (wasm32 + iOS constraint)

|---|---|---|---|---|

| **hnsw_rs** | **Yes** | likely (no C deps) | bincode dump + data mmap | MIT/Apache-2.0 |
| **usearch** | No (C++ via `cxx`) | **iOS yes; wasm via JS binding** | single-file mmap / `view_from_buffer` | Apache-2.0 |
| **arroy** | algorithm yes; **LMDB (C)** | iOS yes; **wasm NO** | LMDB KV entries | MIT |
| **faiss** | No (C++/BLAS) | no | monolithic file | MIT |

Implications:
- **Hard wasm32 constraint ⇒ pure-Rust only:** `instant-distance` or `hnsw_rs`.
  `instant-distance`'s "serde → bytes → KV value" model fits Slate's store cleanly.
- **USearch** is the best *feature* fit (iOS + view-from-disk + quantization) but
  its Rust path is C++ FFI and its wasm path is the JS binding — a binding-by-target
  split (`slate-uniffi` could use USearch on iOS; `slate-wasm` could not use the
  Rust crate). That asymmetry is a real cost.
- **arroy** can't reach wasm (LMDB), so it's a *template to reimplement*, not a dep.
- Every option is permissively licensed.

> Verification gate before committing to any pure-Rust crate: `cargo build --target
> wasm32-unknown-unknown` for `slate-wasm` and an iOS arch build for `slate-uniffi`.

### 6.3 Persisting an ANN graph in an ordered-KV store vs rebuild-on-open

Three viable persistence strategies, in increasing order of effort:

1. **Flat, no graph (recommended phase 1).** `doc_id → vector bytes` in a CF; query
   = `scan_range` + in-memory top-k heap. Zero ANN-persistence problem; exact;
   maps perfectly onto `scan_range`. Matches Cosmos `flat` and sqlite-vec.
2. **IVF over KV.** Centroids in a small KV entry; posting lists keyed
   `(centroid_id, doc_id)` → one `scan_range` per probed cell. Training is offline
   (rebuild centroids periodically). Clean KV fit (§3.6).
3. **Graph (HNSW/Vamana) over KV — hardest.** Either (a) **persist adjacency as KV
   values** (DiskANN-style co-location: `node_id → {neighbors, vector/PQ code}`,
   PQ codes cached in RAM, beam-batched reads — the arroy/Hannoy/LSM-VEC path), or
   (b) **rebuild the in-memory graph on open** from the stored vectors (simplest;
   bounded by corpus size; what many embedded HNSW libs do — but startup cost and
   RAM grow with N). For on-device small corpora, **rebuild-on-open** is often
   acceptable and sidesteps the incremental-persistence problem entirely.

The fundamental tension (§3.6): graph search = serially-dependent random `get`s,
the KV store's worst pattern; flat/IVF = range scans, its best.

### 6.4 Filtered vector search (pre vs post-filter) in a document DB

Slate already has a planner with sargable secondary-index predicates — the natural
advantage here. Options (§4.2):
- **Pre-filter:** resolve the metadata predicate via existing indexes → a candidate
  doc-id set → brute-force `VECTORDISTANCE` over just those vectors. **For flat,
  pre-filter is free and exact** (no graph to disconnect) — a strong reason flat is
  attractive for a *filtered* document DB.
- **Post-filter:** ANN top-N then drop non-matches (risk: <k results).
Cosmos's `filterPriority` spec param hints they blend the two for DiskANN; Slate
can start with pre-filter-into-brute-force, which is both simpler and more accurate.

### 6.5 Memory / size limits for on-device

- **A 1536-dim float32 vector = `4*1536 + 8` ≈ 6,152 bytes (~6 KB)** (pgvector
  formula, §2.3). 100K such vectors ≈ **600 MB** of raw float data alone — material
  on a phone.
- **Quantization matters a lot on mobile:** SQ (int8) = 4× smaller (~1.5 KB),
  BQ (1 bit) = 32× smaller (~192 bytes) with rescoring. `float16`/`halfvec` = 2×.
  Cosmos parity already gives a `dataType` of `float16`/`int8`/`uint8` to lean on
  (§2.1).
- **HNSW adds the graph on top** of the floats (`d*4 + M*2*4`/vector) and wants to
  be RAM-resident — doubly costly on-device. This is another argument for
  **flat + optional quantization first**, ANN graphs later.

### 6.6 Suggested phasing (for the eventual RFC to decide)

1. **`VECTORDISTANCE` function** (`slate-eval`) + a **flat** vector index
   (`doc_id → vector`, `scan_range` + top-k), `cosine`/`dotproduct`/`euclidean`,
   `TOP k` in SQL — Cosmos `flat` parity, exact, KV-native, filter-friendly.
2. **Quantization** (`int8`/`float16`, then binary + rescore) for on-device
   footprint — Cosmos `quantizedFlat`-ish.
3. **ANN** (IVF over KV first — clean range-scan fit; or a pure-Rust HNSW with
   rebuild-on-open) for large on-device corpora — Cosmos `diskANN`-ish.

   favors flat-first for an embedded store; §1.5, §3.1, §3.6.)
2. **ANN persistence strategy** *if/when* pursued — **rebuild-in-memory on open**
   vs **persist the graph as KV values** (DiskANN co-location) vs **IVF-over-KV**
   (range scans). (§3.6, §6.3.)
3. **Crate dependency vs build-our-own** — pure-Rust `instant-distance`/`hnsw_rs`
   (wasm-safe) vs USearch (best features, but C++ FFI + per-target binding split)
   vs reimplement the arroy KV scheme. (§2.4, §6.2.)
4. **Quantization & dtype support** — float32 only, or `float16`/`int8`/binary
   (Cosmos parity + on-device footprint), and whether to keep full-precision
   vectors for rescoring. (§3.3, §6.5.)
5. **Filtered-search semantics** — pre-filter-into-brute-force (reuse Slate's
   planner/indexes; exact) vs post-filter vs blended; and the `VECTORDISTANCE`
   surface (signature, metric param, `TOP k`) for Cosmos parity. (§2.1, §6.4.)
